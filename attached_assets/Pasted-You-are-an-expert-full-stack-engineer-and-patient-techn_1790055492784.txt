You are an expert full-stack engineer and patient technical mentor.

Build a complete, clean, modular, production-minded web application called “AskData” that converts natural-language questions into safe SQL queries, executes them against a sample SQLite database, and displays the results in a chat-style interface.

The application must be easy for a Python and FastAPI learner to understand. Do not generate a vague prototype or only describe the solution. Create the working application files, connect the frontend and backend, seed the database, and explain the important code after implementation.

==================================================
1. PRODUCT GOAL
==================================================

The user should be able to type questions such as:

- “Show the top 5 customers by total revenue.”
- “How many orders were placed in each city?”
- “List products that cost more than 100.”
- “What was the total revenue for each month?”
- “Which customer has placed the most orders?”

The application should:

1. Accept a natural-language question.
2. Send it to a FastAPI backend.
3. Provide the backend-owned database schema to an LLM.
4. Generate a SQL query.
5. Validate that the SQL is safe and read-only.
6. Execute the query against SQLite.
7. Return the generated SQL, columns, rows, and useful errors.
8. Display the SQL and results clearly in the frontend.
9. Allow the user to inspect the sample database schema.
10. Allow results to be exported as CSV.

The application must never allow users or the LLM to modify the database.

Frontend:

- Use simple CSS, Tailwind CSS, or another lightweight styling approach.

LLM:

- Read the API key only from an environment variable.

- Include a deterministic mock or placeholder mode that works when no LLM API key is configured.

Database:

- SQLite database file named data.db.
- The backend must own and provide the schema.
- Seed the database with realistic sample data.
- Open the database in read-only mode for query execution.
- Never trust a schema sent by the frontend.

5. NATURAL-LANGUAGE-TO-SQL FLOW
==================================================

Implement the flow using separate modules:

1. Receive and validate the question.
2. Load the backend-owned schema.
3. Build an LLM prompt containing:
   - The schema.
   - Table relationships.
   - SQL rules.
   - Several question-to-SQL examples.
   - The current user question.
4. Call the LLM provider.
5. Clean the returned text:
   - Remove Markdown code fences.
   - Remove accidental explanations.
   - Extract the SQL statement if necessary.
6. Validate the SQL.
7. Add LIMIT 100 if the query does not already contain a safe limit.
8. Execute the query in read-only mode.
9. Return columns and rows.
10. If execution fails, optionally retry with the database error and schema.

Implement a maximum of three total LLM attempts:

- Initial SQL generation.
- First repair attempt after a database or syntax error.
- Second repair attempt if needed.

Do not retry indefinitely.

==================================================
6. SQL SAFETY REQUIREMENTS
==================================================

This is a critical requirement.

Only allow read-only queries.

Accept:

- SELECT statements.
- WITH statements that ultimately contain a SELECT, if safely validated.

Reject:

- INSERT
- UPDATE
- DELETE
- DROP
- ALTER
- CREATE
- REPLACE
- VACUUM
- ATTACH
- DETACH
- PRAGMA
- LOAD_EXTENSION
- Multiple statements
- Comments or payloads that attempt to bypass validation
- Queries that access files or external databases

Use both:

1. A clear keyword and statement-count safety check.
2. SQL parsing with SQLGlot or an equivalent parser when possible.

Do not rely only on a query beginning with the word SELECT.

Use SQLite read-only connection settings. If the database is missing, provide a clear startup error explaining how to create it.

All responses must be limited to a maximum of 100 rows unless a stricter limit is requested by the user.

Protect against:

- Very large result sets.
- Invalid table names.
- Invalid column names.
- Empty questions.
- Extremely long questions.
- LLM output containing explanations instead of SQL.
- SQL injection attempts included in the natural-language question.

Put the provider-specific implementation in a separate module.

- Support a mock mode when no API key exists.
- The mock mode should recognize a few example questions and return valid SQL.
- If the mock mode cannot answer a question, return a clear error rather than pretending to understand it.
- Keep API-specific code separate from prompt construction and SQL validation.
- Never expose the API key to the frontend.

Use a prompt similar to:

“You generate SQLite SQL only. Return exactly one SQL statement and no Markdown, explanation, or comments. Use only the tables and columns in the provided schema. The query must be read-only and must return no more than 100 rows.”

Include at least five few-shot examples.
